# .kiro/steering/ · Steering 规则集

> 本目录下的每个 `*.md` 都是一条**对 agent 生效的持久性规则**。它们是 `/AGENTS.md` 的细化,粒度更具体、更易增删。
>
> **你(agent)在开始任务前,应当先判断这次任务触及了哪些主题,再去读对应的 steering 文件。**

## 目录

| 文件 | 主题 | 什么时候应该读它 |
|---|---|---|
| [harness.md](./harness.md) | Harness Engineering 核心约束(总则) | **所有任务都必读** |
| [code-style.md](./code-style.md) | 代码风格与命名 | 所有涉及代码编写的任务 |
| [testing.md](./testing.md) | 测试约定 | 所有涉及代码改动的任务 |
| [security.md](./security.md) | 安全与权限红线 | 所有任务都必读;涉及网络/凭证/输入处理时着重 |
| [docs.md](./docs.md) | 文档、ADR、注释标准 | 改接口、改行为、改架构的任务 |
| [git-workflow.md](./git-workflow.md) | Git / PR / 提交规范 | 所有任务 |
| [DEPRECATION.md](./DEPRECATION.md) | Harness 退役台账(老化对抗) | 新增/修改 harness 条目的任务必看 |

## 如何新增一条 steering

1. 先问:**这是不是一条"反复出现的痛点"**?只出现一次的偶发问题不应成为 steering 条目。
2. 选一个**已经存在的主题文件**放进去。如果实在不匹配,新建一个文件,同时:
   - 在本 README 的目录里加一行。
   - 在 `DEPRECATION.md` 里登记这条 steering 是否针对当前模型版本,什么条件下可复审。
3. 通过 PR 修改(走 `harness-change` 标签)。

## 格式约定

每条 steering 条目建议遵循这个模板:

```markdown
### <一句话主题>

**适用范围**:哪些任务 / 哪些文件 / 哪些场景适用?

**规则**:(明确的、可执行的、不留二义的)

**示例**:
- ✅ 正确做法
- ❌ 错误做法

**理由**:(为什么存在这条规则 —— 是为了对抗哪种失败模式?)

**退役条件**:(可选)什么条件下这条可以删除或简化?
```

`**理由**` 不是可选项——没有"为什么"的 steering 会在半年后变成没人敢删的化石。

## 不要做的事

- ❌ 把 steering 当 README 用(会淹没关键规则)。
- ❌ 把"上次任务的临时 prompt 补丁"复制成 steering(应该先判断是不是重复问题)。
- ❌ 把 steering 和业务文档混写(文档去 `docs/`)。
- ❌ 写"应该 / 尽量 / 最好" —— 要写"必须 / 不得",或干脆别写。

## 与 AGENTS.md 的关系

- **AGENTS.md = 仓库级基线**(流程、职责、红线、命令集)。
- **steering/*.md = 按主题的细化规则**(风格、测试、安全、文档、git……)。
- 两者冲突时:**以严的那条为准**;无论哪份文件,**安全红线永远最高**。
